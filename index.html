01 BlueBow Group 2025 · London In production

Customer dashboard performance rewrite

The first screen 30,000 people saw every month took three seconds to appear, and half of what it showed was already out of date.

3.1s→0.8s median load
  • React
  • TypeScript
  • React Query
  • REST
Ask me about this one

Problem

Every panel on the dashboard fetched its own data on mount, then fetched it again on every tab switch. Nothing was shared, nothing was cached, and users regularly acted on numbers that were minutes stale. Support was fielding roughly fifteen tickets a month that all traced back to the same root cause.

Process

I measured before I touched anything. Profiling the network waterfall showed the same three endpoints being hit four times on a cold load. I mapped which data was genuinely shared across panels, took a migration plan to two senior engineers, and moved one panel first as a proof rather than proposing a big-bang rewrite.

Solution

A single shared query layer with keyed caching, background refetching, and cache invalidation tied to write operations, so the UI updates itself instead of waiting to be told. Spinners were replaced with skeleton states matched to the real layout, which stopped the page shifting as data landed.

Outcome

Median load dropped from 3.1s to 0.8s and the stale-data tickets stopped. The pattern was picked up on two other screens by the rest of the team, which I think mattered more than the numbers did.

02 BlueBow Group 2025 · London In production

Billing API and role-based access control

The highest-risk part of the product was also the least tested. I built the new endpoints, and put a net under the old ones first.

34%→76% test coverage
  • Node.js
  • Express
  • PostgreSQL
  • JWT
  • Jest
Ask me about this one

Problem

A new admin tier needed billing endpoints that didn't exist yet. The existing payments service sat at 34% coverage — enough to feel safe, not enough to be safe — and permission checks were scattered through individual route handlers where they were easy to forget.

Process

I wrote the endpoint contract and agreed the schema in review before writing implementation code. Then I backfilled tests around the existing payment paths first, so refactoring them had something underneath it. Roles were modelled explicitly rather than inferred from a scatter of boolean flags.

Solution

A validated REST endpoint set with schema-level input validation at the boundary and role-based access control enforced in middleware, not in handlers — so a new route is protected by default rather than by remembering. Database constraints do the work the application layer shouldn't be trusted with.

Outcome

Coverage went from 34% to 76%, and the new tests caught two regressions before they reached release. The endpoints are still running in production.

03 Personal project 2025 · Ongoing Live

Clarity — note-taking built for ADHD brains

Capture was never the problem. Retrieval was. So I built the app around getting things back out.

Grew out of my final-year project · in daily use
  • React
  • AWS Lambda
  • DynamoDB
  • Cognito
  • GitHub Actions
View the code

Problem

Most note apps quietly assume you'll come back later and organise. For people with ADHD that assumption is exactly where the system fails: notes go in fast and never come out, and the app becomes one more place to feel behind.

Process

I started from the failure point rather than the feature list. Talking through how people actually use these apps narrowed it to three moves worth designing for: dump it fast, have it summarised, get the actions out. Anything that didn't serve one of those three got cut.

Solution

A React front end on a serverless API — Lambda behind API Gateway, Cognito for auth, DynamoDB for notes. Summarisation runs on save and pulls actionable tasks into their own list. Semantic search means you can find a note by what it was about rather than what you happened to call it. Real-time sync keeps phone and laptop honest.

Outcome

It started as my final-year project and it's the note app I actually use. Automated tests and a CI/CD pipeline mean I can still ship to it a year later without needing a careful mood.

04 Acumen Digital 2024 · Client work Live

Restaurant ordering flow, rebuilt

The owner thought it was the prices. The funnel said it was the four-step checkout and the forced account.

Baseline→+22% completed orders
  • Next.js
  • Headless CMS
  • REST
  • Vercel
Ask me about this one

Problem

A local restaurant had a site that took online orders but rarely finished them. People arrived, browsed the menu, and left somewhere between the basket and the confirmation. The owner's theory was pricing.

Process

I looked at the funnel before touching the design. Drop-off clustered at two points: the moment the site demanded an account, and a menu that reflowed unusably on phones — where most of the traffic was coming from. That reframed the job from redesign to removal.

Solution

Guest checkout, four steps collapsed into two, and a basket that survives a page reload. The menu became one scannable list with sticky category navigation on mobile. Built on Next.js with a headless CMS so the owner could change prices and specials without calling me.

Outcome

Completed online orders rose around 22% over the first two months. The owner has been updating her own menu ever since, which was the part of the handover I cared most about.

05 Personal project 2024 Testnet

Blockchain e-voting system

Electronic voting asks people to trust a database they can't see. The interesting problem is making the count checkable without exposing the voter.

Deployed to Ethereum Sepolia · end-to-end demo
  • Solidity
  • Ethereum Sepolia
  • Node.js
  • Express
View the code

Problem

A voting system has to satisfy two things that pull against each other: anyone should be able to verify the result, and nobody should be able to link a vote to a person. A conventional back end asks you to take both on trust.

Process

I read how existing approaches handle it, then wrote the contract before the interface — the guarantees had to be settled before any of the UI decisions made sense. Registration, casting and tallying were modelled as separate stages with explicit transitions, so an invalid sequence is impossible rather than merely discouraged.

Solution

Solidity smart contracts handling voter registration, one-vote-per-address casting, and automatic tallying at close. A Node and Express service sits alongside for everything that has no business being on-chain, keeping gas costs and stored data to what actually needs to be public.

Outcome

Deployed to the Sepolia testnet with a working end-to-end demo. It taught me more about state machines, immutability and the cost of a bad schema than anything else I've built.

How I work

Four habits I've earned the hard way.

  • Measure before you touch it

    I don't trust my instinct about what's slow. The dashboard rewrite started with a profiler rather than an opinion, and the profiler disagreed with everyone — me included.

  • Make the safe path the default path

    Permission checks belong in middleware, not in handlers. Constraints belong in the database. If correctness depends on someone remembering, it will eventually be forgotten.

  • Ship the smallest real version

    I'd rather migrate one panel and prove the pattern works than propose a rewrite and spend two weeks defending it in meetings. Working code is a better argument than a document.

  • Write it down for the next person

    The onboarding docs I wrote at BlueBow are still used by every new starter. Of everything I did there, that's the one I'm quietly most pleased with.
